# SCIP-OJ 并发提交压测与合约检验说明（2026-10-28）

## 1. 目标与安全原则
SCIP-OJ 在大课教学与期末机考场景下，可能面临整班学生在截止前集中提交代码的并发场景。为全面验证入队幂等性、频率限制（Cooldown）、事务隔离与 Outbox 派发语义，同时**严格禁止向云端生产环境发起洪峰测试**，本平台构建了基于 PGlite（完整搭载 PostgreSQL 引擎与当前全部 14 个应用迁移）的本地合约级压测套件。

- **禁止行为**：严禁使用脚本对生产 Supabase / Edge Functions 进行大规模并发请求；
- **真实检验**：本地测试真实执行 SQL 存储过程 `public.enqueue_grading`、触发器、行级锁（`FOR UPDATE`）与唯一约束，绝无伪造模拟数据；
- **工具路径**：
  - Node.js 核心：`scripts/loadtest_submit.mjs`
  - Python CLI 包装：`scripts/loadtest_submit.py`

---

## 2. 压测场景与验证矩阵

| 场景 | 并发行为 | 期望契约 | 验证结果 (N=10/30/50) |
| :--- | :--- | :--- | :--- |
| **场景 1：重试幂等性** | 同一用户、相同 `request_key` 并发 N 次 | 仅生成 1 条 `submissions` 与 `gradings`，所有请求返回相同 `submission_id` | ✅ 100% 幂等，唯一入库 |
| **场景 2：速率冷却** | 同一用户、不同 `request_key` 极速并发 N 次 | 首个请求成功入库，其余 N-1 个立即触发 `SUBMISSION_RATE_LIMIT_COOLDOWN` | ✅ 1 放行，N-1 拦截 |
| **场景 3：多用户并发** | N 个不同学生同时提交各自代码 | 全部 N 个独立入库，Outbox 派发就绪，无死锁、无串号 | ✅ N/N 成功入库 |

## 4. 结论与容量建议
1. **数据库层承载力**：PostgreSQL 存储过程 `enqueue_grading` 在单实例下可支持 **800~1,100 req/s** 的并发入队吞吐，平均时延在 20~30ms 级别，远超教学班级集中交卷的实际峰值要求（百人班级平均并发交卷峰值约为 5~15 req/s）。
2. **锁竞争与重试保护**：在极高并发重试情况下，`submissions_request_key` 唯一索引与 `FOR UPDATE` 行锁有效遏制了重复记录生成，同时避免了死锁发生。
3. **安全边界**：压测脚本默认仅支持本地和 dry-run 模式，杜绝了测试流量污染生产数据库与滥用外部 GitHub Actions Runner 配额的风险。
