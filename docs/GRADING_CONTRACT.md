# 正式提交与成绩契约

## 数据归属

`submissions` 保存不可变源码；`gradings` 保存一次评测及当时的配置；`grading_dispatches` 是仅服务端可读的派发待办和私有实例种子。教师复判和自动恢复都追加 grading，不增加学生提交次数。

学生、单条复判和批量复判共用 `enqueue_grading`。源码、首个评测和待办在同一个事务中提交；复判同时写入教师审计。失败整体回滚，避免补偿删除和“已保存但没有评测”的记录。已有配额、课程权限、学号及考试身份核验在事务内执行。

浏览器不能直接写 submissions、gradings 和 grade_audits，也不能读取待办。内部 RPC 使用 SECURITY INVOKER，只授权 service_role；Edge 必须先通过 `auth.getUser` 认证，再传入已确认的用户 ID。已登录浏览器不能直接调用内部 RPC 冒充其他用户。

## 重试与任务归属

客户端发送 UUID `request_key`。同一用户的相同请求返回原 receipt，同键不同内容返回冲突；重放原请求不再次占用配额。网页在响应丢失时保留请求键，刷新后可继续重试；只保存摘要和键，不在该记录中另存源码。存储不可用时仅在当前页面内保留重试身份。

批量复判按稳定列表分片，并由一个操作键派生每片和每条请求键。部分已成功后网络失败，重试相同列表和原因不会再建一份已成功任务；网络异常不会触发全新单条请求的静默回退。改变目标列表或原因视为新操作。

派发待办使用两分钟租约和 `SKIP LOCKED` 领取。派发接受后十分钟仍未认领可重发；传输失败按指数退避，单次任务最多派发五次。派发超时不立即宣告失败，因为远端可能已接受。Actions 必须原子认领 grading；重复运行未认领成功时，不执行源码也不发送评分回调。

认领后的运行器标识包含 GitHub run ID 和 run attempt。一个 Actions 的手动重新运行也不能冒用上一次认领；应通过平台复判或自动恢复创建新评测。

恢复工作流每五分钟计划执行一次，单轮最多派发二十五项。GitHub 的定时触发可能延迟，这不是五分钟出分保证。运行超过二十分钟或派发次数耗尽时记系统故障；最新任务允许最多两次自动恢复。恢复沿用同一配置、评分器版本和私有实例种子。达到上限后保留故障，教师可以人工发起新的复判。旧历史评测不会被批量重写。

## 评分版本和可信边界

接受评测时解析服务端仓库 main 的完整提交 SHA，冻结题目、评分策略版本、测试数量和及格线。执行端签出该 SHA，使用固定题目文件和评分器。无法确定版本时，新请求不被接受；已接受请求的幂等回放仍可返回记录。

私有随机实例种子留在仅服务端可读的待办中，只给受信任评分器。学生容器收到公共实例字段，不能读取最优值、私有种子、服务密钥或可信评分代码。恢复可重放同一批实例，不将种子放入报告。回调报告记录源码哈希、评分器 SHA、实际构建镜像 ID 和评分配置。

镜像 ID 提供执行审计，但本项目尚未归档每个 Docker 镜像，也未锁定整个系统包仓库；因此不能据此承诺任意日期逐比特复现镜像。若需严格环境重放，需增加按 digest 发布和留存镜像。

部署交接时，旧版 Edge 已接受但没有快照的排队任务，允许在首次认领时冻结当前配置，并显式标记 `legacy_at_claim`。这不等同于恢复当初不存在的配置快照，也不改写历史成绩。

## 状态与成绩

| 状态 | 含义 | 分数 |
| --- | --- | --- |
| queued | 源码与评测已保存，等待运行器认领 | null |
| running | 唯一运行器已认领 | null |
| done | 可信评分完成，包括学生程序错误或错误解 | 0–100 整数 |
| system_error | 评测基础设施故障 | null，不能作为学生零分 |

完成回调先验证 HMAC，再由一个数据库事务检查任务、提交和运行器归属，写入终态并回填教师审计。重复相同结果不重复计分，已成功结果的冲突回调被拒绝。自动恢复成功后回填其所属教师复判审计。Actions 对相同签名请求进行有限重试；彻底丢失回调则由运行超时恢复处理。

学生与教师共用 `grading-state.js`：`latestAttempt` 是最新任务，`effectiveGrade` 是该份提交最新一次成功评分。新任务排队或故障不抹去有效分数；成功降分则替换旧高分。按创建时间及 ID 排序，与成绩簿保持一致。课程通过判定使用作业当前及格线；原评测报告仍保留执行时冻结的及格线。

课程成绩最终由数据库成绩簿按作业的 highest_before_due、highest 或 latest 策略计算，前端不另算最终课程总成绩。课程教学与拓展案例的成绩路径继续分开。

## 部署与验证

1. 先应用 `20261026054644_reliable_grading_lifecycle.sql`，再部署新 callback。
2. 合并并启用新的评测与恢复工作流，接着部署 submit-assignment、regrade、regrade-batch。旧 Edge 的服务端写入保持可用，过渡任务按上述 legacy 合同处理。
3. Pages 发布新的请求键和成绩模块。检查数据库 RPC 授权、私有表访问限制、Edge 版本及恢复工作流运行状态。
4. `npm run test:database` 在本地嵌入式 PostgreSQL 执行完整迁移和事务失败注入；CI 使用 PostgreSQL 17 的独立连接验证并发请求与租约竞争。`npm run test:grading` 验证前端成绩和重试身份；既有判题、考试、仿真及真实 Notebook 回归继续执行。

生产中的真实师生完整验收仍需授权测试账号和隔离测试课程。没有执行这一步时，应明确区分代码/数据库验证与真实课堂验收。
