# SCIP-OJ 正式评分标准 v2 — 预注册提案与隔离实现（尚未上线）

状态：2026-10-23 提案。judge/score_policy_v2.py 为独立纯函数原型；现有 L1/L2、已有学生成绩与 Supabase 均未更改。**不得把本文当作已经启用的正式评分政策。**

## 0. 最重要的裁决

课程必须把三件事区分：

1. **OJ 单题算法分（0–100）**：是否返回了满足硬约束的结果，是否正确或足够优。
2. **工业工程案例评价（0–100）**：学生是否真的建模、验证、设计实验、解释统计不确定性及工程决策。这一部分有独立人工/证据量表。
3. **课程总评**：教师按教学大纲把多个 OJ 作业、实验报告、课程项目、考试组合成课程总成绩，必须课程开课前冻结每一部分的权重。

不得为单个 OJ 解的“格式正确”或“约束没违反”直接赋大量创新或性能分；更不能用一个 100 分总分混淆算法正确性、仿真论证和报告表达。

## 2. OJ 单题评分：两种题型，不允许一套公式通吃

### 模式 E：精确优化题（P001/P002 当前应优先采用）

模型：学生提交 solve(instance)->dict。服务端独立校验解向量、整数性、全部硬约束、解目标值重算和已证最优目标。若其中任何一步失败，则相应实例判错；如果目标非最优，即使可行也不能得到该实例的精确解得分。

- 每个私有用例的得分资格为 AC（所有检查通过），否则 0。
- 3 个基础用例组成 Basic 组，权重 20；
- 4 个边界用例组成 Boundary 组，权重 30；
- 5 个压力用例组成 Stress 组，权重 50。
- 一组内全部测试满足才拿满该组分；未满足，组分为 0。单题最后分数 = 三组相加。
- **通过条件 = 所有私有用例均 AC**。默认展示通过线 90 只是兼容字段；在精确题上，真正 AC 必然 100 分。
- 部分分反映在哪些子任务达标，不能把部分分称为通过。
- 公共示例输入可供无限练习，正式权重为 0；正式隐藏测试实例数为建议 12，实际由课程评测基准校准后冻结。

### 模式 A：近似优化与启发式题

仍先强制所有格式、约束、整数、资源可用性检查通过。不合理或不可执行方案该实例质量分必须为 0，不能把超低目标值当作成绩。

在基线与**独立已证最优**可靠、且基线严格差于最优的情况下，才对可行方案使用无量纲质量：

\[
q_i =
\begin{cases}
\mathrm{clip}\bigl((z_{\mathrm{base}}-z_i)/(z_{\mathrm{base}}-z^*),0,1\bigr),&\text{最小化},\\
\mathrm{clip}\bigl((z_i-z_{\mathrm{base}})/(z^*-z_{\mathrm{base}}),0,1\bigr),&\text{最大化}.
\end{cases}
\]

若优化基线等于最优，分母为零，该用例不能用此公式，应转精确测试。若学生目标声称优于已证最优，则应进入 checker 异常复核，禁止简单封顶后直接出分。

子任务分：

\[
S_g = w_g\min_{i\in g}q_i,\qquad
S=\operatorname{round}_{\mathrm{half\ up}}\!\left(\sum_g S_g\right).
\]

- 这是**相对基线的性能达成率**，不是 SCIP solver optimality gap；二者定义、分母和科学含义不同。
- 只用主机独立复算得到的可行性/目标，不接收学生自己报的 q 或 status。
- 最终通过：所有硬约束用例都可执行且 S≥90；含一个硬约束失败，即使剩余用例使分数≥90，也显示“部分分、未通过”。
- 如果某复杂实例只得到 best known 而非 certified optimum，可将其用于非正式练习排名；在完成基准和目标冻结前，不得伪装成“相对最优差距”并计正式分。
- 不给时间越短自动加额外分：在本平台的课程评分中，CPU/时间/内存为资源上限；同等测试环境、稳定性和程序输出的正确性优先。

## 3. 严重错误、系统故障和四种不同分数

| 运行状态 | 单实例质量 | 是否可正式通过 | 反馈 |
|---|---:|---|---|
| AC + 精确最优 | 1 | 可以 | 已满足该测试 |
| AC + 近似可行 | [0,1] | 与总分和全局 Gate 共同决定 | 可行、相对基线质量 |
| FORMAT_ERROR / WA | 0 | 否 | 返回格式或正确性不符 |
| INFEASIBLE / NON_INTEGRAL | 0 | 否 | 硬约束/整数性失败（不披露私有实例） |
| OBJECTIVE_MISMATCH | 0 | 否 | 自报目标与独立重算不同 |
| TLE / RE / MEMORY_LIMIT | 0 | 否 | 学生代码运行失败 |
| SYSTEM_ERROR / TEST_CONTRACT_MISMATCH | 无分数 (null) | 不计为学生不及格 | 基础设施故障，自动恢复/重判 |

必须将以下 UI 字段区分展示：numeric_score、accepted/passed、judge_status、gradebook_policy_version。不能用 95 分自动推断 passed；不能用 system_error 的 0 扣学生总评。

## 4. 工业工程《系统建模与仿真》案例评分：单独量表

P001/P002 的 OJ 自动判分不能替代 IE-DES-01 的实验报告评分。

案例实验按现有《课程实验与评价规范》继续使用六维人工/证据评分（合计 100）：

| 维度 | 权重 | 最低核验证据 |
|---|---:|---|
| 业务问题与边界 | 15 | 系统边界、工业工程目标、合成/实测来源 |
| 数学模型与事件逻辑 | 20 | 状态、事件、方程、资源/约束 |
| 独立验证 | 20 | 手算/独立程序、边界测试和守恒 |
| 实验设计与统计 | 20 | 配对 CRN、独立重复、区间与反例 |
| 工程分析与决策 | 15 | 效率成本权衡、方案建议的前提 |
| 复现与表达 | 10 | 运行 manifest、原始 CSV/JSON、软件/seed/图表 |

其中独立验证和数据复现可以由 OJ 辅助判题；**统计设计是否支撑因果/工程结论、业务边界合理性和报告论证仍需要课程评价**。不要将客户端答题框自报说明直接当成正式分。

课程总评（作业、实验、期末/项目的权重）应由教师在课程大纲确定并冻结；平台只提供可配置项，不擅自替教师设定 60/40 或 50/50。

## 5. 不可变评分合同：出分前必须固定的证据

每个正式提交绑定以下信息：

- policy_schema_version、assignment_version、published_at；
- problem_id、grader_id、grader_version、judge_git_sha；
- score_mode、各 subtask 权重、通过线、积分/可行性容差、资源上限；
- case manifest / generator version 与不可公开的 seed derivation key version；
- immutable submission id / code sha256、提交时间与迟交标记；
- 结果中的状态、各组得分、申诉/重判记录和原评分版本。

客户端不得控制评测元数据；服务器必须在提交入库时以可信快照固定它。重新判定默认使用原提交版本，不在后台临时读取老师后来修改的 assignments 行。更改政策应新增版本，历史成绩默认不重写；如确需全班重评，须由教师确认一套批量重判规则并保留审计。

与尚未合并的重放 PR #19 和 #20 的评分合同冻结/调度恢复配合使用，**不可只合入评分公式就认为生产安全已完成**。

## 6. 反事实 / 对抗验收

- T01：全零向量只可行不最优，精确题该用例 0，不存在先给 55 的结果。
- T02：19 个 AC 与 1 个 INFEASIBLE，不能靠平均值达到 90 并通过。
- T03：单组含任意错误，该组按最低质量计分；所有组满分必为 100。
- T04：无效或超时返回不应从格式、积分、约束获得额外奖励。
- T05：系统基础设施/缺用例产生 status=system_error 且 score=null；不能冒充学生0分。
- T06：近似题基线与最优相等、数值无穷、NaN、声称超越独立已证最优等情形拒绝。
- T07：相同冻结输入/版本/源代码重评应产生相同结果；密钥轮换要保留旧 key-id 或明确申诉期限。
- T08：超载队列、不可执行调度、违反 AGV/起重占用应作为硬约束而非用好看的 Cmax 抵消。
- T09：教师新发布版本不得改变旧提交分数；即使全班批量重评，需提供改动表。
- T10：新方案以参考解、已知错误解、随机解、输入硬编码、复杂度边界多种提交评测。

## 7. 从原型转向线上 L2 的放行顺序

G0 教师确定该题到底是精确还是近似；评分权重 20/30/50 只是初始预注册提案，需题集难度校准，不是当前正式已发布规则。

G1 验证每个测试组针对一种独立能力，至少覆盖 12 个多尺度、边界和对抗输入；精确 oracle 可交叉验证。

G2 学生 solve(instance) 结果由服务器独立解析、可行性/整数性/目标核验，再交给 score_policy_v2；不能信任学生传入的 verdict 或 quality。

G3 完成 immutable policy、原子提交/调度与失败恢复。只有这些准备好才改实际 runner 与 Supabase UI。

G4 对既有提交运行双轨影子判分，比较 legacy vs v2（分布、错误类型、False-Pass、False-Fail）；经教师审核再公告切换时间。

G5 学生、教师真实账号进行提交、限流、成绩查看、复判、申诉全流程验证；再允许正式课程启用。

**目前已完成的只是纯函数原型与其回归测试，不代表新规则已经实施。**
