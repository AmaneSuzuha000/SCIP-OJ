Run the Python kernel in a worker so a hung cell can be stopped

The interpreter lived on the main thread, so an infinite loop in a lesson cell
froze the tab: no repaint, no button, no way out but force-quitting the browser.
The graded path was never at risk -- that runs in an isolated container with its
own timeout -- but the practice path had no limit at all.

Pyodide's interrupt buffer would be the cheaper fix, except it needs a
SharedArrayBuffer and therefore COOP/COEP headers, which GitHub Pages does not
send. So the interpreter moves into a worker, where the answer to a runaway cell
is terminate(): the kernel is rebuilt on next use instead of the page dying.

A 60s watchdog turns a hang into a normal failed cell with a message saying the
environment was reset and earlier variables are gone. It is generous because the
notebooks solve small MILPs in seconds; it only has to catch code that will
never finish.

Timeouts and crashes share one path, abort(): the worker is terminated, every
caller still waiting is resolved with a failure rather than left on a promise
that never settles, and the handle stays usable. loadKernel caches a booted
kernel and retries a failed one.

Verified in Chromium against a real build, not just the mock: the worker chunk,
pyodide.mjs, the wasm, the numpy and scipy wheels and pyscipopt.py all load, and
a cell in lesson 06 executes to the no-output marker.

4 new tests stub the Worker boundary and pin the three outcomes: a result comes
back, a hang becomes a TimeoutError with the worker terminated, and the kernel
still works afterwards with a fresh worker. 53 web tests pass, tsc clean.
